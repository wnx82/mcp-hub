# Roadmap — Migration MCP HUB vers MCP 2026-07-28

## 1. Objectif

Adapter **MCP HUB** à la spécification **Model Context Protocol 2026-07-28** sans casser les clients existants ni les garanties de sécurité du projet.

La migration doit notamment permettre :

- l’utilisation du nouveau cœur MCP sans session au niveau du protocole ;
- la compatibilité avec les nouvelles versions des SDK MCP ;
- le maintien du fonctionnement actuel en `stdio` ;
- la préparation ou la migration du transport HTTP Streamable ;
- le maintien du mode `READ_ONLY` ;
- la conservation de la compatibilité avec les anciens clients lorsque le SDK le permet ;
- l’ajout de tests de non-régression ;
- une migration progressive, documentée et réversible.

## Étape 05 — Adaptation au protocole sans session

### Objectif

Faire en sorte que chaque requête MCP puisse être traitée indépendamment d’une session de transport.

### Actions

- [x] Supprimer toute dépendance applicative à `Mcp-Session-Id` pour la nouvelle version du protocole.
- [x] Ne plus supposer que `initialize` précède obligatoirement chaque requête.
- [x] Ne plus supposer que deux requêtes successives arrivent sur la même instance.
- [x] Vérifier que chaque appel reçoit toutes les informations nécessaires.
- [x] Ajouter des arguments explicites lorsqu’un outil dépend d’un contexte fonctionnel.
- [x] Éviter tout état critique stocké uniquement en mémoire locale entre deux appels.
- [x] Maintenir la compatibilité avec les anciennes versions si le SDK la gère.

### Constat du 2026-08-01

- Aucune dépendance protocolaire à `Mcp-Session-Id` ou à un ordre `initialize -> request` n'a été trouvée dans le hub
- Les workflows multi-appels critiques suivants ne dépendent plus uniquement de la mémoire locale:
  - `plan_mutation` / `confirm_mutation`
  - `destroy_resource` avec confirmation en deux temps
- Les confirmations sont maintenant persistées dans `state.db` via des handles opaques, expirables, et indépendants d'une session de transport
- Cela réduit le risque qu'un redémarrage du processus invalide arbitrairement une confirmation encore valable
- Les outils n'attendent pas qu'un appel precedent fournisse un contexte volatile de type `select_host`
- Les cas de ciblage implicite restants comme `DEFAULT_HYPERVISOR` proviennent d'une configuration statique de deploiement, pas d'une session de transport ni d'un ordre d'appel
- Les connexions SSH persistantes et certains caches non critiques restent des optimisations techniques ou des caches applicatifs distincts, à traiter séparément si nécessaire

### Exemple de règle

Un outil comme :

```text
list_vms
```

ne doit pas dépendre d’un appel précédent comme :

```text
select_host
```

sauf si l’identifiant de l’hôte ou un descripteur d’état est explicitement transmis.

### Critères de validation

- [x] Deux appels indépendants peuvent être exécutés sans session partagée.
- [x] Un appel fonctionne même après redémarrage du processus lorsque l’état n’est pas censé être persistant.
- [x] Les outils ne dépendent plus d’un ordre implicite d’appel.
- [x] Le mode `READ_ONLY` reste inchangé.
