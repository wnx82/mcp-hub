# MCP 2026-07-28 Migration Guide

This document summarizes the MCP Hub migration to the `2026-07-28` Model
Context Protocol revision, the resulting compatibility posture, and the
rollback procedure if an operator must return to the previous release line.

## What changed

- MCP Hub now targets the Python `mcp` SDK `2.0.0`.
- The server bootstrap supports the modern `MCPServer` runtime and still keeps
  the compatibility fallback needed by older SDK imports when applicable.
- Streamable HTTP requests are handled as stateless calls and no longer depend
  on a transport session identifier.
- Mutation confirmations can now use either:
  - explicit persistent `state_handle` / `confirmation_token` flows
  - MRTR `input_required` retries for MCP `2026-07-28` clients
- The server can now be started explicitly on `stdio` with
  `mcp-hub --transport stdio` or `MCP_TRANSPORT=stdio`.

## Compatibility matrix

| Element | Previous state | Current state | Status |
| --- | --- | --- | --- |
| SDK MCP | `mcp 1.28.1` / `FastMCP` baseline | `mcp 2.0.0` / `MCPServer` target | Migrated |
| `stdio` | Not confirmed in the pre-migration audit | Explicit startup path via `--transport stdio` | Supported |
| SSE | Not used | Still not used | Not applicable |
| HTTP Streamable | Primary transport | Primary transport with stateless header validation | Supported |
| Claude Code | Documented HTTP client | Documented HTTP client | Supported |
| Claude Desktop | Not directly supported with bearer token auth | Still requires an OAuth-capable gateway | Limitation documented |
| Legacy handshake clients | Supported as far as the SDK keeps compatibility | Accepted when the SDK supports them | Best effort |
| MCP `2026-07-28` clients | Not available on the old SDK line | Supported, including MRTR for guarded mutations | Supported |

## Operator migration checklist

1. Upgrade the package dependencies so the runtime installs `mcp>=2,<3`.
2. Regenerate or reinstall the environment from `requirements.txt` or the
   package metadata.
3. Start with `MCP_READ_ONLY=true`.
4. Validate:
   - `mcp-hub --version`
   - `python -m unittest`
   - `python3 scripts/generate_tool_reference.py --check`
5. Re-check any reverse proxy to preserve:
   - `Authorization`
   - `MCP-Protocol-Version`
   - `Mcp-Method`
   - `Mcp-Name`
6. If a local client needs stdio rather than HTTP, launch with
   `mcp-hub --transport stdio`.

## Known limits after migration

- Claude Desktop still cannot connect directly to MCP Hub while the hub uses a
  static bearer token instead of OAuth.
- Real multi-instance HTTP validation depends on the operator's own proxy or
  load balancer and cannot be proven from the repository alone.
- Real target-system integrations still depend on the operator's fleet,
  credentials, and network reachability.

## Rollback procedure

If you must roll back from the MCP `2026-07-28` line to the prior release
family:

1. Check out the pre-migration reference release or commit.
   - Previous public baseline: `0.3.0`
   - Migration target release: `0.4.0`
2. Restore the dependency set that pins:
   - `mcp==1.28.1`
   - matching `requirements.txt`
3. Reinstall the environment from the restored tree.
4. Restart the service in `READ_ONLY` first.
5. Re-run the same smoke checks:
   - `mcp-hub --version`
   - unit tests
   - one read-only discovery call

Operational consequences of rollback:

- MCP `2026-07-28` MRTR flows disappear.
- Stateless HTTP header validation specific to the modern protocol disappears.
- The runtime returns to the legacy SDK line and its older bootstrap model.
